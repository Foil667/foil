ERC-8048 is a metadata add-on, not a new identity.

Keep ERC-8004 as the canonical identity and trust rail. Mirror useful agent profile fields into ERC-8048 only when your NFT contract—or a sidecar—can support it cheaply. The technology is coherent; the ecosystem commitment is not yet proven.

01 / THE PRIMITIVE

One read function. Arbitrary bytes. Auditable writes.

The official Draft standard extends ERC-721, ERC-1155 or ERC-6909 token registries with a generic key–value lookup. It requires EIP-165, EIP-7930 and EIP-8119. The getter’s ERC-165 interface ID is 0xdf670be1.

IERC8048Metadata.sol
function metadata(uint256 tokenId, string calldata key)
  external view returns (bytes memory);

event MetadataSet(
  uint256 indexed tokenId,
  string indexed indexedKey,
  string key,
  bytes value
);

// Optional; write policy is set by the contract.
function setMetadata(
  uint256 tokenId, string calldata key, bytes calldata value
) external;
ERC-721T PROFILE

Reserved agent keys

context, endpoint[mcp|a2a|web|x402], address[chain-id], and optional additional account[…][index] entries. It is a convention inside the spec, not a separate interface ID.

TOKENURI UNCHANGED

Wallet-safe adoption

Marketplaces continue reading familiar visual metadata. Agent-aware clients call metadata() for operational fields; older clients simply ignore them.

OPTIONAL AUTHORITY

Writes need not follow ownership

IERC8048MetadataAuthority can assign field governance to a separate authority. Its interface ID is 0xf9cb127d.

SIDECAR PATH

Existing collections can join

A top-level metadata_contract field in token JSON may point to an external contract implementing the getter—an adoption path added after Normies NFT feedback.

Fact source: official ERC-8048 specification. The spec itself warns clients to treat context and endpoint values as untrusted input.

02 / THE STACK

8048 stores. 8004 establishes trust.

They are deliberately orthogonal, but their edges overlap enough to create real fragmentation risk.

ERC-8004

Identity + trust

  • Identity, reputation and validation registries
  • Profile via a URI-addressed registration file
  • Optional onchain getMetadata / setMetadata
  • The ecosystem’s current identity rail
STACK
ERC-8048 / 721T

Metadata + discovery

  • Generic token-level key–value storage
  • Context, service endpoints and accounts onchain
  • No reputation or validation mechanism
  • Can attach directly to an existing NFT
The collision: ERC-8004 already exposes getMetadata(); ERC-8048 standardizes metadata(). Both are Draft, both use similarly shaped MetadataSet events, and no published convergence path exists.
03 / THE “FUTURE” CASE

Why the idea is bigger than its interface.

This section is synthesis, not settled fact: it explains the strongest case behind the “future” claim.

Zero-pin profiles

Descriptions, endpoints and accounts can be read through RPC without depending on an IPFS pin, HTTPS host or gateway.

NFT-native agents

An ordinary collection can gain machine-readable behavior while retaining its existing marketplace-facing tokenURI.

Payment-ready discovery

Reserved x402 endpoints and per-chain addresses turn a token into a discoverable service and account map.

Cross-chain proofs

The optional Diamond Storage layout creates predictable slots intended to support storage-inclusion proofs.

Governed metadata

A metadata authority can manage regulated or curated fields without becoming the NFT owner.

05 / FRICTION

The unresolved parts matter.

DESIGN

Scope creep

Discussion participants challenged the extensions as too opinionated. The author agreed some could eventually split into separate ERCs.

GAS

Dual-key event

The event emits a hashed indexed key and the plaintext key. A co-author called that redundant; the author defended plaintext discovery.

INDEXING

No key enumeration

There is no core keys(). Clients must know keys in advance or index historical events.

ECOSYSTEM

Competing surfaces

metadata() and ERC-8004’s getMetadata() may leave implementers supporting two similar Draft interfaces.

SECURITY

Untrusted values

Onchain does not mean safe. Context strings and endpoint URIs can still carry malicious or misleading payloads.

TRACTION

Thin evidence

The main discussion had roughly 14 posts over about a year; verified usage is dominated by testnet and roadmap signals.

07 / PRACTICAL MOVE

Duplicate the profile. Preserve the identity.

Opinionated recommendation for an already ERC-8004-registered agent:

NOW

Keep 8004 canonical

Do not abandon its identity, reputation or validation rails. ERC-8048 cannot replace those layers.

PILOT

Mirror a small key set

Use an upgradeable agent NFT or the sidecar pattern. Start with context, web/MCP endpoints and the relevant chain address.

ESCALATE WHEN

Readers appear

Adopt broadly after Review/Final status, multiple indexers query 0xdf670be1, or counterparties ask for it directly.

Open questions before committing gas

  • No authoritative registry of ERC-8048/721T mainnet deployments or usage volumes was found.
  • No independent gas benchmark was found for the claimed ERC-721T cost advantage over an ERC-8004 registry.
  • The event-design PR outcome was not independently confirmed; the 2026-09-28 spec still showed the dual-key event.
  • The original “ERC-8048 is the future” X post could not be independently verified beyond the supplied mission context.

Sidecar skeleton (Solidity)

RabbitHole8048Sidecar.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

// 8048 sidecar: keeps metadata() off your main NFT contract.
interface IERC8048Metadata {
    function metadata(uint256 tokenId, string calldata key)
        external view returns (bytes memory);
    event MetadataSet(
        uint256 indexed tokenId,
        string indexed indexedKey,
        string key,
        bytes value
    );
}

contract RabbitHole8048Sidecar is IERC8048Metadata {
    address public owner;
    mapping(address => bool) public curators;
    mapping(uint256 => mapping(string => bytes)) private _kv;

    constructor() { owner = msg.sender; }

    modifier onlyCurator() {
        require(msg.sender == owner || curators[msg.sender], "not curated");
        _;
    }

    function metadata(uint256 tokenId, string calldata key)
        external view override returns (bytes memory) {
        return _kv[tokenId][key];
    }

    function setMetadata(uint256 tokenId, string calldata key, bytes calldata value)
        external onlyCurator {
        _kv[tokenId][key] = value;
        emit MetadataSet(tokenId, key, key, value);
    }

    function setCurator(address who, bool ok) external {
        require(msg.sender == owner, "not owner");
        curators[who] = ok;
    }
}
